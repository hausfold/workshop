A shared rice is an ordinary `.nix` file that changes only `haus.*`.
Keeping that boundary small makes the result easy to inspect, combine with
other rices, and override from a host file.

## The format

The file evaluates to an attribute set whose only top-level key is
`haus`:

```nix
{
  haus = {
    developer.enable = false;
    prowl.enable = false;
    keys.leader = "none";

    theme = {
      flavor = "latte";
      accent = "rosewater";
    };

    sill.items.weather = false;

    tour.steps = [
      {
        hint = "Press {palette}, type tour, then hit ↵";
        detect = "palette";
      }
    ];
  };
}
```

It is not a module function: there is no `{ pkgs, lib, config, ... }:` header.
It also does not set `system.defaults`, install packages, or add activation
scripts. Every setting stays inside the documented
[`haus.*` option surface](/reference/options/).

<Aside type="tip" title="Whole rice or layer?">
A **whole rice** describes a kind of machine or person and usually chooses all
the big rooms: developer tools, tiling, the bar, and the launcher. A **layer**
describes one concern, such as larger text, and sets only what that concern
needs. Layers are easier to compose because they leave unrelated choices alone.
</Aside>

## Validate the boundary

Run the same structural check as nebelhaus's built-in presets:

```sh
nix eval --impure --expr \
  '(builtins.getFlake "github:hausfold/hausfold").lib.checkRice ./writer.nix'
```

If the file is an app **pack** — only `haus.roster`, the apps on a machine —
run `lib.checkPack` instead. It is the same rule one level in, and it is what
makes the pack safe to import through `lib.pack` below.

It prints `true`, or throws with the top-level key that escaped the data-only
boundary. `checkRice` is the trust-boundary check; it does not prove that every
option name or value is valid.

For that, import the rice into a real host:

```nix
extraModules = [ ./rices/writer.nix ];
```

Then evaluate the configuration before activating it:

```sh
nix eval .#darwinConfigurations.myhost.system.drvPath
```

If that succeeds, `haus rebuild` still gives you the usual build-before-apply
safety.

## Test composition, not just isolation

A useful rice should survive being combined with a layer and then overridden
by its user:

```nix
extraModules = [
  ./rices/writer.nix
  nebelhaus.presets.large-print
];
```

Before publishing, try:

- the rice by itself;
- the rice plus an unrelated layer;
- a host value set on top of one of the rice's own choices;
- each combination of rooms you turn off.

For the middle two of those you need neither a Mac nor a build. The nebelhaus
repo checks its own presets exactly that way — `nix flake check`'s
`preset-composition` composes every pair of them through `lib.evalModules` over
the option surface alone, in seconds, and diffs the answers against a table.
(Evaluating a rice *by itself* is a different check, `presets`, and that one does
raise a whole darwin system.) Composition is the one property a rice cannot have
on its own, which is what makes it the one worth testing before you publish.

### The composition rule, in one line

**Two rices compose unless they *disagree*.** Import order carries no priority,
so "imported after, therefore wins" is not a mechanism you can lean on in either
direction — but naming the same option is not the problem people assume it is:

- **Same option, same value** — fine. Nix merges identical definitions, so a
  rice that restates a value the consumer already holds costs them nothing.
- **Same option, different values** — the build stops, and tells you plenty:

  ```text
  error: The option `haus.sill.enable' has conflicting definition values:
         - In `…/presets/minimal.nix': false
         - In `…/presets/everyday.nix': true
         Use `lib.mkForce value` or `lib.mkDefault value` to change the priority…
  ```

  The option, both files, and the fix. A consumer resolves it with `lib.mkForce`
  in their host — and that line belongs in your README for every field you set
  that a reasonable person might disagree with.

So narrow the rice until ordinary Nix merging is enough: every optional field
you set is one a consumer has to force. A layer that leaves unrelated choices
alone composes; one that restates a whole machine collides with the next layer
along.

<Aside type="caution" title="The quiet half: list and attribute options merge">
The conflict above only happens for options that hold a single value. An option
holding a **list or a set** — `tour.steps`, `roster`, `theme.ports.handled` —
never conflicts at all: the definitions are **combined**, with no error and no
warning. Two rices that each author one tour step produce a tour with both, in
an order neither author chose.

That is the failure mode worth testing for, because nothing will tell you about
it. If your rice authors a tour, say so in its README, and say whether it expects
to be the only one.
</Aside>

<Aside type="note" title="App packs are the exception">
A pack — a rice narrowed to `haus.roster`, the apps on a machine — is
imported through `nebelhaus.lib.pack`, which lowers every field it sets so the
consumer's own host wins with a plain assignment and no `mkForce`. That is a
property of the seam, not of the file: the same pack imported as a bare path
still conflicts. Presets are deliberately not wrapped that way.
</Aside>

## Publish something inspectable

The smallest useful repository is deliberately boring:

```text
writer-rice/
├── README.md
├── writer.nix
└── LICENSE
```

In the README, say:

- who the rice is for and what it changes;
- whether it is a whole rice or a layer;
- which nebelhaus revision you tested;
- how to import it;
- what it deliberately does not handle, including required rooms or
  permissions;
- whether both `checkRice` and a real host evaluation passed.

For a first release, invite people to review and vendor the `.nix` file. A
remote flake wrapper can come later if versioned imports become useful; it
should not hide the data users are being asked to trust.

## What does not belong

Keep these in a private host file or an explicitly more powerful module:

- identity, secrets, tokens, device UUIDs, and personal account names;
- a personal app roster that reveals more than the rice needs;
- raw macOS defaults outside `haus.*`;
- package or store paths that require `pkgs`;
- activation hooks and shell commands.

A configuration that genuinely needs `pkgs`, scripts, or arbitrary
nix-darwin options is a **power module**. That can be useful, but it carries a
different trust model and should be labelled as one.

## Before you share

- [ ] The file has only a top-level `haus` key.
- [ ] `checkRice` prints `true`.
- [ ] A real host configuration evaluates.
- [ ] The rice composes with an unrelated layer.
- [ ] If it sets a list or set option — `tour.steps`, `roster` — the README says
      so, because a second rice setting the same one merges into it silently.
- [ ] Every field the rice sets is listed in its README with the `lib.mkForce`
      line a consumer needs to override it — or, for a pack, imported through
      `nebelhaus.lib.pack` so they don't.
- [ ] Disabled rooms agree with dependent features, including
      [`tour.steps`](/guides/making-it-yours/#the-first-run-tour).
- [ ] The README states the audience, scope, tested revision, and limits.
- [ ] There is no identity, secret, or device-specific data.
