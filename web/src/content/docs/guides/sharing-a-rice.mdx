A shared desktop is an ordinary `.nix` file that changes only `haus.*`.
Keeping that boundary small makes the result easy to inspect, select, and
override from a host file.

A host selects **exactly one** desktop. Desktops do not stack: two of them are
refused by name, because two complete answers to "what should this Mac feel
like?" have nothing to arbitrate them. What you layer on top is your own host
file, and it wins with a plain assignment.

## The format

The file evaluates to an attribute set whose only top-level key is
`haus`:

```nix
{
  haus = {
    developer.enable = false;
    prowl.enable = false;
    keys.leader = "none";

    theme = {
      flavor = "latte";
      accent = "rosewater";
    };

    sill.items.weather = false;

    tour.steps = [
      {
        hint = "Press {palette}, type tour, then hit ↵";
        detect = "palette";
      }
    ];
  };
}
```

It is not a module function: there is no `{ pkgs, lib, config, ... }:` header.
It also does not set `system.defaults`, install packages, or add activation
scripts, and it cannot reach a **host-only** option — identity, secrets, a
signing identity, a display UUID. Every setting stays inside the desktop-safe
half of the documented [`haus.*` option surface](/reference/options/).

## Select it

```nix
darwinConfigurations.myhost = haus.mkNebelhaus {
  username = "ada";
  hostname = "myhost";
  host = ./hosts/myhost;
  desktop = ./desktops/writer.nix;
};
```

One argument, one desktop. Omit it and you get the `nebelhaus` desktop, which
is what every consumer had before the argument existed. `desktop = null` selects
none — the bare haus foundation plus whatever your host turns on, which is also
what the built-in `blank` desktop names.

Composing by hand instead? Pass the desktop through the seam *and* say
`desktop = null`, or the builder's own default becomes your second one:

```nix
desktop = null;
extraModules = [ (haus.lib.desktop ./desktops/writer.nix) ];
```

## Your host wins, plainly

The priority ladder is the whole point of the seam, and it means an ordinary
line in your own host file overrides the desktop you chose — no `lib.mkForce`,
no import-order trick (import order carries no priority in the module system):

| | |
|---|---|
| 100 | your host file |
| 900 | the desktop |
| 1000 | a room's own default |
| 1500 | an option's declared default |

Lower wins. So a desktop must outrank the generic defaults it exists to replace,
and must lose to the person who chose it.

```nix
# your host file — no lib, no mkForce
{
  haus.theme.accent = "teal";   # the desktop said "mauve"
}
```

<Aside type="caution" title="A list your host also names REPLACES the desktop's">
Lists normally concatenate. Across this seam they do not: a host that names
`haus.pounce.autoQuit.exclude` replaces the desktop's list rather than appending
to it, which is the behaviour you want when overriding a whole choice, and a
surprise if you expected to add one entry. Restate the entries you want to keep.
</Aside>

## Validate the boundary

```sh
nix eval --impure --expr \
  '(builtins.getFlake "github:hausfold/haus").lib.checkDesktop ./writer.nix'
```

It prints `true`, or throws naming the file and **every** rule it broke at once:
a module function rather than data, an `imports` or `_module` key, a stray
top-level key, `system.activationScripts`, an option that does not exist, or a
host-only leaf a desktop may not set. `haus.lib.desktopFailures` returns that
list instead of throwing, if you would rather test it than read it.

That check is structural and runs before evaluation. It is not the same as
proving the desktop builds — for that, select it into a real host and evaluate:

```sh
nix eval .#darwinConfigurations.myhost.system.drvPath
```

[`haus plan`](/reference/haus/) is the stronger version of that last step: it
runs a full build, then prints what activation *would* change — packages,
settings, files, launchd jobs, casks — without applying any of it. And
`haus rebuild` still gives you the usual build-before-apply safety on top.

haus checks its own catalogue exactly this way. `nix flake check`'s
`desktop-seam` runs the closed-schema rules against a directory of fixtures —
valid ones and one per class of refusal — and diffs the diagnostics it produces
against a table; `catalogue` raises a whole darwin system from every desktop
this flake ships.

## One concern, not one more desktop

The thing people reach for a second desktop to express — "the same machine, but
readable" — belongs to the room that owns it, as a **profile**:

```nix
haus.appearance.largePrint = true;
```

One line, in a desktop or in your host. It sets the interface scale, the
high-contrast palette, macOS's own contrast lift and the screen's scaled
resolution together, each as a *default*, so any single one of them stays yours
to pin. That is what a cross-cutting concern looks like under one-desktop-per-
host: a room-owned option, not a file to stack.

## App packs

A **pack** is a data-only file narrowed to one option family, `haus.roster` —
the apps on a machine, not the kind of machine it is. It is not a peer of a
desktop; it belongs to the [Apps](/reference/options/#apps) room, and the ones
haus ships are one switch each:

```nix
haus.apps.packs.writing.enable = true;   # Obsidian, Zotero, Anki, calibre
```

Someone else's pack file arrives through the seam that gives it its priority:

```nix
extraModules = [ (haus.lib.pack ./writer-pack.nix) ];
```

`lib.pack` lowers **every field** the pack sets to a default, per leaf, so your
own `haus.roster.obsidian.key = "n"` wins that one field with a plain assignment
and the rest of the pack's entry — the cask that installs it, its name —
survives. That is a property of the seam, not of the file: the same pack
imported as a bare path conflicts the old way. Self-test one with
`haus.lib.checkPack`, which is `checkRice` one level in.

Two packs naming the same app still stop the build, and should: you cannot be
expected to know what is inside a pack, while two pack authors are equals.
Naming that app in your own host settles it, because a plain assignment outranks
both at once.

<Aside type="caution" title="The quiet half: a list option merges instead of conflicting">
Between two *modules at the same priority* — two packs, two `extraModules`
entries — a **list**-typed option (`tour.steps`, `keys.leaderExtras`,
`snippets.matches`) never conflicts at all: the definitions are **combined**,
with no error and no warning. Two files that each author one tour step produce a
tour with both, in an order neither author chose.

It can also surface later as something harder than a merge. Two files each
adding a leader key merge quietly, and *then* prowl asserts that leader keys are
unique and don't reuse a roster app's — a failure at eval that points at neither
file.

**Attribute sets are the middle case.** `roster`, `workspaces` and
`pounce.items` are `attrsOf`, so definitions merge *per key*: two files naming
different apps compose, while two naming the same app's same field conflict as
loudly as any single value. That is deliberate — a silent merge there would
quietly drop somebody's app.

If your file sets any of these, say so in its README.
</Aside>

## Publish something inspectable

The smallest useful repository is deliberately boring:

```text
writer-desktop/
├── README.md
├── writer.nix
└── LICENSE
```

In the README, say:

- who the desktop is for and what it changes;
- which rooms it turns on, and which it deliberately leaves off;
- which haus revision you tested;
- how to select it;
- what it deliberately does not handle, including required permissions;
- whether both `checkDesktop` and a real host evaluation passed.

For a first release, invite people to review and vendor the `.nix` file. A
remote flake wrapper can come later if versioned imports become useful; it
should not hide the data users are being asked to trust, and it owes every
module it wraps a `_file`. Rebuilding an attribute set loses the filename, and a
conflict that reads `<unknown-file>` on both sides is unresolvable by the person
holding it — which is exactly why `lib.desktop` and `lib.pack` both set one.

## What does not belong

Keep these in a private host file or an explicitly more powerful module — a
desktop is *refused* for most of them rather than merely discouraged:

- identity, secrets, tokens, and personal account names;
- raw macOS defaults outside `haus.*`;
- a `pkgs` value, or a `/nix/store` path;
- activation hooks and shell commands;
- a display UUID — `haus.displays.main` names "the screen this Mac is using"
  without naming anyone's hardware, which is what `appearance.largePrint` uses.

**Naming a package is not on that list.** Options that take a package have a
`packageName` sibling taking the nixpkgs attribute as a *string*
(`haus.roster.<name>.packageName`, `haus.fonts.mono.packageName`), and
`nix flake check`'s `data-only-surface` mechanically requires one for every
package-typed leaf. So a desktop can change the mono font or add a tool without
leaving the data-only surface.

A configuration that genuinely needs `pkgs`, scripts, or arbitrary
nix-darwin options is a **power module**. That can be useful, but it carries a
different trust model and should be labelled as one.

## Coming from presets

`presets` was the older name for a shareable file, and it let two of them stack.
Every one still resolves, with a warning naming its replacement, and will be
removed:

| was | is |
|---|---|
| `extraModules = [ haus.presets.full ]` | nothing — `mkNebelhaus` already selects the `nebelhaus` desktop |
| `extraModules = [ haus.presets.everyday ]` | `desktop = haus.desktops.everyday` |
| `extraModules = [ haus.presets.minimal ]` | `desktop = haus.desktops.minimal` |
| `extraModules = [ haus.presets.large-print ]` | `haus.appearance.largePrint = true` |
| `extraModules = [ haus.packs.writing ]` | `haus.apps.packs.writing.enable = true` |
| `lib.checkRice ./my-rice.nix` | `lib.checkDesktop ./my-desktop.nix` (still `lib.checkRice` for a pack file) |

The two rows in the middle are not the same machine they were: as a preset,
`everyday` was four lines layered on top of whichever desktop you had, and as a
desktop it is the whole selection those four lines implied. Read
`desktops/everyday.nix` before you switch — the one deliberate difference is
that it leaves the AI room off, which the preset never mentioned.

## Before you share

- [ ] The file has only a top-level `haus` key.
- [ ] `checkDesktop` prints `true`.
- [ ] A real host configuration evaluates with it selected.
- [ ] A plain host assignment overrides one of its choices, with no `mkForce`.
- [ ] If it sets a list option — `tour.steps`, `keys.leaderExtras` — the README
      says so, because a host that names the same one replaces it wholesale.
- [ ] Disabled rooms agree with dependent features, including
      [`tour.steps`](/guides/making-it-yours/#the-first-run-tour).
- [ ] The README states the audience, scope, tested revision, and limits.
- [ ] There is no identity, secret, or device-specific data.
