Sooner or later you'll want Slack, or Discord, or `ripgrep`, or that one obscure
CLI you saw on a blog. Good news: you almost never touch the rice to do it.

The quickest route is **Install App** in pounce: pick a missing app from the
rice's curated **Popular apps** shelf or search a package source, choose whether
the app belongs in your launcher roster or should only be installed, and pounce
writes a small Nix module plus rebuilds. It is declarative, not a hidden
imperative install.

Prefer to write it yourself? Edit your host config and rebuild:

```sh
haus edit       # opens ~/.config/nix/hosts/<hostname>/default.nix
# …add your app or tool…
haus rebuild    # build, then switch
```

Everything you declare there *merges* with what the rice and pounce-generated
package modules already declare. The only question is **which option** to use.

<Aside type="tip" title="One Nix model, two doors">
Manual entries and **Install App** use the same options. Pounce writes one file
per selection under `hosts/&lt;hostname&gt;/packages/`; `mkNebelhaus`
auto-imports that directory. You can inspect, edit, move, or delete those files
like any other Nix module—there is no separate `roster.json`.
</Aside>

Or let Pounce make the edit: open **Install App** and choose **Popular apps** or
where to search (Homebrew, the Mac App Store, or the flake's pinned Nixpkgs).
The curated shelf hides apps already present on the Mac and does not expose
which package source backs each pick. Each choice is written as a small Nix
module under `hosts/<hostname>/packages/` and applied with `haus rebuild`; a
Homebrew cask or App Store app can also be added to the tiling roster, including
its launcher key and optional workspace. For a workspace app,
Pounce checks the pinned
[SketchyBar App Font mapping](https://github.com/kvndrsslr/sketchybar-app-font)
and writes the verified `barIcon` ligature too. If upstream has no match, the
pill keeps its workspace letter rather than guessing an icon.

<Aside type="note" title="Why App Store installs open a terminal">
Pounce runs `mas get` visibly before any roster rebuild. App Store downloads can
ask for an Apple Account, Touch ID, or sudo, and hiding that inside
`darwin-rebuild` can look like a hung activation. If `mas` cannot acquire the
app, Pounce opens its App Store page instead.
</Aside>

There's nothing to set up first — no data files, no options to point at. Each
selection lands as its own Nix module under `hosts/<hostname>/packages/`, and
Pounce stages and commits just that file after a successful rebuild.

## One list: `nebelhaus.roster`

Everything the machine has goes in the same roster — apps, fonts, CLI tools,
Nixpkgs packages, App Store apps. You don't choose an *option*; you choose which
**fields** to set, and that's what the entry means:

<CardGrid>
  <Card title="A GUI app I'll live in" icon="laptop">
    Set **`key`** and **`workspace`**: a Caps-Lock letter, its own workspace, a
    bar pill, the auto-tiling rule, a cheatsheet row — and it installs it.
  </Card>
  <Card title="A GUI app, no fuss" icon="download">
    Omit `key` and `workspace`. The entry is just an install: nothing bound,
    nothing drawn, still declared.
  </Card>
  <Card title="A CLI tool I'll keep" icon="seti:shell">
    Same list, no launcher fields — just **`package`** (nixpkgs) or **`brew`**
    (a formula). `scope` decides user profile vs system-wide.
  </Card>
  <Card title="A CLI tool, just once" icon="magnifier">
    Trying something out? Run it **without installing** via `,` (comma). Nothing
    to clean up.
  </Card>
</CardGrid>

Four sources, one per package manager — set the one that applies:

| field | installs from | example |
|---|---|---|
| `cask` | Homebrew cask | `cask = "slack";` |
| `brew` | Homebrew formula | `brew = "ical-buddy";` |
| `package` | your flake's pinned nixpkgs | `package = pkgs.ripgrep;` |
| `appStoreId` | the Mac App Store | `appStoreId = 497799835;` |

Set none of them and the entry is pure metadata — right for something already on
the machine (Safari, Music) that you still want a launcher key for.

### The rice's own apps are entries too

You don't have to know which apps nebelhaus already installs. Each room declares
its own: `den` gives `ghostty` its cask, `prowl` gives `aerospace` its, `sill`
`sketchybar`, `snippets` `espanso`. Trill, Pounce and Perch copy a notarized
bundle into `/Applications` from their own activation step — neither a cask nor
a package — so they carry `installedBy` instead.

The practical effect: when you add a leader key for an app the rice ships, you
write only the launcher half.

```nix
# Trill's name, bundle id and installer come from nebelhaus.trill.
nebelhaus.roster.trill = {
  key = "m";
  workspace = "M";
  barIcon = ":messages:";
};
```

The rule underneath is *whoever installs an app owns its source fields, whoever
gives it a key owns the launcher fields* — so two modules never fight over one
field, and your host file never explains what the rice is doing. `haus doctor`
and the [agent skill](/guides/ai-agent/) both read the merged result, so
"what's on this machine and who put it there" has one answer.

<Aside type="note" title="Why one list and not four">
`homebrew.casks`, `homebrew.brews`, `home.packages` and
`environment.systemPackages` all still work and still merge. But reaching for
them for an *app* means declaring it in two places the moment you want a
launcher key — and worse, **nothing warns you.** Homebrew's lists concatenate
and `brew bundle` is idempotent, so a cask named in two places just installs
twice, in two locations, forever. (That's not hypothetical: it's how a
`homebrew.casks = [ "iina" ]` sat beside the rice's own `pkgs.iina` for months —
back when IINA came from a bare package line rather than the roster entry
[the rice declares today](#the-apps-the-rice-picks-for-you).)

The roster catches it now — same id merges, and a name that appears twice in the
final Homebrew lists is a build warning. The plain lists stay as the escape
hatch for the rare thing that isn't an app at all, like a tap.
</Aside>

## A GUI app with a launcher key (the roster)

This is the nebelhaus-native way to add an app you actually work in. One keyed
entry in `nebelhaus.roster` wires up *everything at once*: a Caps-Lock letter to
launch/focus it, a workspace it lives on, a pill in the bar, the auto-tiling
rule, a row in the cheatsheet — and it installs the app for you.

```nix
nebelhaus.roster.slack = {
  key = "s";
  name = "Slack";
  workspace = "S";
  appId = "com.tinyspeck.slackmacgap";
  barIcon = ":slack:";
  label = "Slack";
  cask = "slack";
};
```

Rebuild, and tapping <kbd>⇪</kbd> then <kbd>S</kbd> launches Slack onto
workspace `S`, every time.

The two fields people always have to look up:

- **`appId`** — the app's bundle id, used to auto-send its windows to the right
  workspace. Find it once the app exists on disk:

  ```sh
  osascript -e 'id of app "Slack"'
  # → com.tinyspeck.slackmacgap
  ```

- **`barIcon`** — a ligature from the
  [SketchyBar app font](https://github.com/kvndrsslr/sketchybar-app-font)
  (e.g. `:slack:`, `:discord:`, `:figma:`). Browse the list on that page; leave
  it `null` and the bar just shows the workspace letter.

<Aside type="tip" title="Declaring it is what installs it">
`cask = "slack"` means the entry **also installs** Slack — no second line
anywhere. Leave every source field unset for an app that's already on the
machine (Safari, Music, something you dragged in) but you still want a launcher
key for.
</Aside>

The full field-by-field breakdown — and the one-app-per-workspace thinking
behind it — lives in [Window management](/guides/window-management/#your-app-roster)
and [Making it yours](/guides/making-it-yours/#the-one-app-per-workspace-idea).

<Aside type="tip" title="It may theme itself on the way in">
If the name you key the entry under matches a tool nebelung has a theme for —
`zed`, `warp`, `xcode`, `rio`, `gitui`, `kitty` and a few dozen more — the
Nebelung theme file lands where that app looks for themes on the next rebuild,
in your flavor, contrast and accent. Some apps pick it up on their own; others
need one click you'll find waiting in `haus doctor`. See
[Theming ▸ Apps you added yourself](/guides/theming/#apps-you-added-yourself).
</Aside>

## A GUI app, no launcher key

Some apps you just want *installed* — a background utility, something you open
from Spotlight-muscle-memory, a thing you touch once a month. Same roster, minus
the launcher fields:

```nix
nebelhaus.roster = {
  discord = { name = "Discord"; cask = "discord"; };
  figma   = { name = "Figma";   cask = "figma"; };
};
```

No `key`, so no Caps-Lock letter and no cheatsheet row. No `workspace`, so no
pill and no auto-tiling rule. It's simply installed — and, crucially, *declared*,
which is what stops [`cleanup = "zap"`](/guides/making-it-yours/#homebrew-behaviour)
from removing it later.

`name` is optional here too, but worth setting: it's what `open -a` uses, and
it's what shows up when a tool lists your machine back to you.

Don't know the cask name? Search it:

```sh
brew search --cask obsidian
```

<Aside type="caution" title="Homebrew apps live outside Nix's time machine">
Casks are installed *by* the rebuild but aren't tracked in Nix generations — so
`haus rollback` won't uninstall an app you added, and won't bring back one you
removed. Removing a cask from your config also won't delete the app by default
(`nebelhaus.homebrew.cleanup` is `"none"`, on purpose, so nothing you installed
by hand ever vanishes). To actually remove one: `brew uninstall --zap <cask>`.
See [Making it yours](/guides/making-it-yours/#homebrew-behaviour) for the
`cleanup` / `autoUpdate` / `upgrade` knobs.
</Aside>

## App Store apps

Some apps only live in the Mac App Store. The smooth path is **Pounce → Install
App → Mac App Store**: type a search, choose the Mac-compatible result, then
install it alone or give it a roster key and workspace. Pounce already knows the
result's numeric App Store id and bundle id.

That path uses [`mas get`](https://github.com/mas-cli/mas) in a visible floating
terminal — visible on purpose, because App Store installs need root and mas asks
for your password or Touch ID, which a silent rebuild would have nowhere to show.

By hand, an App Store app is a roster entry like any other:

```nix
nebelhaus.roster.xcode = {
  name = "Xcode";
  appStoreId = 497799835;   # the digits in its App Store URL
};
```

Recording the id is always safe. **Installing** from it is opt-in:

```nix
nebelhaus.appStore.install = true;
```

Then a rebuild fetches any `appStoreId` entry that isn't already installed. It's
off by default because it reaches the network and acts on your Apple Account —
that shouldn't happen as a side effect of turning on a window manager.

<Aside type="caution" title="What the App Store can't do, exactly">
- **mas cannot sign in.** Do it once in App Store.app, per machine.
- **mas cannot buy a paid app**, ever. Purchase it once in App Store.app; after
  that any machine can install it.
- **Free apps it can fetch outright** — `mas get` acquires an app you've never
  had. (`mas install` is the narrower one: already-purchased only.)

So an unpurchased paid app is *reported and skipped* during a rebuild, never
fatal. And note the rice does **not** use nix-darwin's `homebrew.masApps`: that
runs `mas install` as you through `brew bundle`, hits the root requirement, and
stops for a password prompt the rebuild can't display — a hung activation.
</Aside>

## Already-installed apps

For anything already on the machine — Safari, Music, an app you installed by hand
— you don't need to install it again. Add a roster entry with no source field at
all and it's pure launcher wiring:

```nix
nebelhaus.roster.music = {
  key = "m";
  name = "Music";
  workspace = "M";
  appId = "com.apple.Music";
  barIcon = ":apple_music:";
};
```

## The apps the rice picks for you

A few apps arrive without you asking, because a machine the rice calls finished
should have them. They live in their own room — `nebelhaus.apps` — and each is
one switch:

```nix
# IINA, the video player. On by default; it also takes over the video file
# types macOS hands QuickTime Player, TV and your browser.
nebelhaus.apps.videoPlayer.enable = false;          # don't install it at all
nebelhaus.apps.videoPlayer.claimFileTypes = false;  # install it, rebind nothing
```

The distinction the room draws: an app a *room needs to work* belongs to that
room (prowl brings AeroSpace because it **is** the tiler), while an app the rice
merely **chooses for you** belongs here, behind a switch. What it installs is an
ordinary roster entry, so you can give IINA a launcher key
(`nebelhaus.roster.iina.key = "v";`) or pin a different build without leaving
the list everything else lives in.

The file types are the ordinary user default — the same record Finder's *Get
Info ▸ Change All* writes — so nothing here is hard to undo. The claimed list is
short on purpose (mp4, m4v, mov, mpg, mpeg, mkv, webm, avi, wmv, flv, 3gp, ogv,
vob): audio, `.gif`, playlists and dead or professional containers like `.rm`,
`.mxf` and `.dv` are never touched, and neither is the transport-stream trio
`.ts`/`.mts`/`.m2ts` — on a developer's machine those are TypeScript far more
often than video, so the [editor
hijack](/reference/options/#nebelhaushearthhijackfileassociations) owns them.

<Aside type="caution" title="One owner per type">
That last exclusion is a rule, not a preference. Two rice-owned apps claiming
the same file type never settles into a winner: both claims are re-applied on
every activation, so macOS stops and asks you which app should win — on every
single rebuild. `.mts` really did sit in both lists, and because `.mts` and
`.m2ts` share one AVCHD UTI, the prompt covered both. If you add an extension to
either list, check it against the other **by UTI, not by spelling**.
</Aside>

## A CLI tool you want to keep

Command-line tools normally come from **nixpkgs**, which makes them declarative,
reproducible, and roll-backable. **Pounce → Install App → Nix packages** searches
the exact Nixpkgs revision pinned by your flake and writes a roster entry under
`hosts/<hostname>/packages/`. By hand it's the same list as everything else — a
tool just has no launcher fields to set:

```nix
nebelhaus.roster = {
  ripgrep = { package = pkgs.ripgrep; };
  httpie  = { package = pkgs.httpie; };
  ffmpeg  = { package = pkgs.ffmpeg; };

  # A formula, when nixpkgs doesn't have it (or brew's build is the one you want)
  ical-buddy = { brew = "ical-buddy"; };
};
```

Not sure of the exact package name? Search nixpkgs:

```sh
nix search nixpkgs ripgrep
# …or browse https://search.nixos.org/packages
```

### `scope` — your profile, or the whole machine

`scope` applies to `package` only (Homebrew has no such split):

- **`"user"`** (the default) → home-manager's `home.packages`. Right for
  anything you run as yourself.
- **`"system"`** → `environment.systemPackages`. Installed once for the machine,
  so it's on `PATH` for **root, launchd jobs, and non-login shells** — which is
  what a tool called by a daemon or a `sudo` workflow actually needs.

```nix
nebelhaus.roster.age = {
  package = pkgs.age;
  scope = "system";   # a launchd job needs to find it
};
```

It's about *reach*, not about needing elevated privileges to install —
`darwin-rebuild` runs under `sudo` either way. When in doubt, leave it at
`"user"`.

<Aside type="note" title="Where the rice's own tools live">
The rice ships a baseline toolbelt already (`bat`, `fzf`, `lazygit`, `jq`,
`gh`, `delta`, `yazi`… — see [The shell](/guides/the-shell/)). Those live in the
**nebelhaus repo**, not your host file; only edit them if you're changing the
shared distro for everyone. *Your* machine's extras belong in your host file's
roster.
</Aside>

## A CLI tool, just to try it

hearth wires up [`nix-index`](https://github.com/nix-community/nix-index) and
`comma`, so you can run **any** command in nixpkgs without installing it — great
for one-offs and "does this even do what I think":

```sh
, cowsay "hello fog"     # fetches cowsay, runs it, keeps nothing
, ncdu                   # try a disk-usage TUI once
```

If you find yourself reaching for it twice, *then* give it a roster entry.

## Tools that need a secret or an env var

Some CLIs want an API key. Keep the secret **out of your Nix config** (it'd land
in the world-readable Nix store) — read it from a file at shell startup instead:

```nix
home-manager.users.${username} = {
  programs.zsh.initContent = lib.mkAfter ''
    export OPENAI_API_KEY="$(cat ~/.secrets/openai 2>/dev/null)"
  '';
};
```

The `~/.secrets/*` files stay on the machine, ungit-tracked. See
[Making it yours](/guides/making-it-yours/#secrets--private-things) for the
pattern.

## Then apply it

<Steps>

1. `haus rebuild` — builds first, so a typo can't take down your running system.

2. New casks install, new CLI tools land on your `PATH`, and any new roster app
   gets its letter, workspace, and bar pill — all in one go.

3. If a new roster app doesn't tile on first launch, it's a one-time hiccup;
   tap <kbd>⇪</kbd>, then <kbd>Backtick</kbd> to re-sort everything to its
   workspace.

</Steps>

<Aside type="tip" title="This is your file — go wild">
Your host file is a plain nix-darwin module. Anything nix-darwin or
home-manager accepts works here and merges with the rice. Adding apps is just
the most common case — see [Making it yours](/guides/making-it-yours/) for the
whole cookbook.
</Aside>
