The whole system shares one palette: **[nebelung](/reference/palette/)**, a
silver-mist Catppuccin variant. It's Catppuccin with the blue pulled out of the
greys and the accents calmed down — a fog-grey scheme for people who find most
dark themes too loud. Grey is the point.

nebelung renders that one palette onto **50+ tools** — Ghostty, zellij, starship,
bat, delta, lazygit, fzf, yazi, helix, btop, Slack, the Zen browser, and more —
so the terminal, editor, git, and browser all speak the same colours. The rice
wires up the ones it installs for you; the rest are one roster entry away (see
[Apps you added yourself](#apps-you-added-yourself)).

Three knobs, in the order most people reach for them:

| Option | What it changes |
|---|---|
| [`theme.accent`](#swapping-the-accent) | the one hue that tints highlights |
| [`theme.contrast`](#contrast) | how far text separates from its background |
| [`theme.flavor`](#light-mode) | dark or light |

They compose, and all three take effect on the next `haus rebuild`.

## Swapping the accent

The neutral greys stay fixed; only the **accent** hue changes. Set it once in
your host file:

```nix
haus.theme.accent = "sapphire";
```

Then `haus rebuild`. The accent re-tints the tools that render per-accent
variants — **lazygit** borders, **fzf** highlights, **yazi**, and the **Zen
browser**. Yazi's `glow` Markdown headings use that same accent in both the side
preview and fullscreen pager — while the single-file dotfiles (Ghostty, starship, tmux, bat,
zellij) keep their built-in theme. The generated desktop follows it too — the
bloom behind the mark in `minimal`, and the whole sweep in `bold` — as does any app in your
[roster](/guides/adding-apps/) whose nebelung port ships a per-accent matrix
(`zed`, `gh-dash`, `mpv`).

That list is not prose anyone has to keep true by hand: the rice's
`accent-reach` check fingerprints every one of those surfaces under three
different accents on each `nix flake check`, and fails if one starts — or stops
— following the accent.

<Aside type="caution" title="Zen means Zen's UI, not the web">
The accent moves Zen's own chrome. It does **not** re-tint github.com or
youtube.com, because those aren't styled by anything the rice writes: the
Catppuccin userstyles are LESS, compiled inside the browser, so they live in the
**Stylus** extension's storage rather than in a stylesheet — each carrying its
own accent variable that defaults to `mauve`.

Declare the extension and the rice closes that loop:

```nix
haus.zen.extensions.stylus = { };
```

It deploys Stylus (via Firefox's enterprise-policy file — `haus.roster`
can't install add-ons) and stamps nebelung's userstyle bundle from **your**
theme: the accent, the flavor, and the contrast it's rendered for. All three
axes on this page reach the web.

The import itself stays a click — Stylus has no file interface — so whenever you
change one of them, activation prints a one-time nudge and you do:
**Stylus ▸ Manage ▸ Import ▸ `~/.config/nebelhaus/nebelung-stylus.json`**.
</Aside>

### Available accents

The default is `mauve`. Any of the 14 Catppuccin accent names works:

`rosewater` · `flamingo` · `pink` · `mauve` · `red` · `maroon` · `peach` ·
`yellow` · `green` · `teal` · `sky` · `sapphire` · `blue` · `lavender`

See their exact hex values on the [palette reference](/reference/palette/).

<Aside type="tip" title="Pounce and Perch follow too">
The [Pounce](/guides/pounce/) launcher and the Perch notch shelf compile the
nebelung variants in, so their UI matches the rest of the rice out of the box —
and each loads any other palette at runtime, from `~/.config/pounce/themes/` and
`~/.config/perch/themes/`. The rice installs every nebelung variant in each and
names the one `theme.flavor` / `theme.contrast` select, so they follow those
options like every other tool — no rebuild involved. Perch has no picker of its
own — the rice's word is final, and it always tracks the macOS light/dark
appearance.
</Aside>

## Contrast

The default greys are deliberately soft. If text doesn't separate enough from its
background — a bright room, a glossy screen, or just eyes that prefer more edge:

```nix
haus.theme.contrast = "high";
```

Same hues, same accents; the neutral ramp is pulled apart in OKLCH so every step
gains separation. Body text goes from **11.3:1** to **19.9:1** against the
background, which is measured in nebelung's CI rather than eyeballed — and having
now been looked at on a real screen, it reads crisp rather than harsh.

<Aside type="caution" title="What it reaches, and what it doesn't">
This recolours everything the rice colours — Ghostty, bat, delta, lsd, yazi,
zellij, glow, starship, lazygit, the bar, Zen, Obsidian. It does **not** touch
native macOS apps, which have their own switch:

```nix
haus.accessibility.increaseContrast = true;
```

The two are complementary, and a genuinely high-contrast Mac wants both. That
one needs Full Disk Access on whatever you rebuild from — see its
[option reference](/reference/options/#hausaccessibilityincreasecontrast).
</Aside>

## Light mode

```nix
haus.theme.flavor = "latte";
```

Light mode is **not** the dark palette inverted. nebelung is "Catppuccin with the
blue stripped out", and that recipe says nothing about dark — so it's applied to
Catppuccin **Latte** instead of Mocha to get the same theme in the other
polarity: the same warm-grey neutral ramp, the same calmed accents, read the
other way up.

Because it's a real re-render rather than a recolour, tools take their light-mode
branches properly — terminal ANSI black/white swap around, the Zen browser
switches its `prefers-color-scheme` block, delta marks itself `light = true`.

Light mode lands at **7.0:1** for body text on its own, so it's legible before
you reach for contrast. The two axes compose:

| | `contrast = "normal"` | `contrast = "high"` |
|---|---|---|
| `flavor = "mocha"` | 11.3:1 | 19.9:1 |
| `flavor = "latte"` | 7.0:1 | 9.9:1 |

<Aside type="caution" title="macOS's own appearance is opt-in">
By default the rice leaves **System Settings ▸ Appearance** alone, in both
directions, so a light rice on a dark Mac looks half-finished. One option
finishes it:

```nix
haus.theme.systemAppearance = "flavor";  # latte → Light, mocha → Dark
```

`"light"` and `"dark"` pin it instead, and the default `"unmanaged"` is what
leaves it alone. The default stays hands-off on purpose — a managed default
would silently undo an appearance you picked in System Settings on your next
rebuild.

Three things worth knowing. It is applied with AppleScript rather than a
`defaults` write, because on macOS 26 that key is **inert in both directions** —
it is where macOS mirrors the appearance it's showing, not a lever you can pull
(measured; `haus diff` says so if you declare it by hand). Driving it needs an
**Automation** grant for whatever runs your rebuild
(System Settings ▸ Privacy & Security ▸ Automation); without it the rice tells
you and leaves the appearance alone, and nothing else is affected. And if
System Settings ▸ Appearance is set to **Auto**, macOS switches polarity on its
own schedule — the rice sets it at rebuild time and doesn't fight it afterwards,
so pick Light or Dark there if you want this to stick.

**Pounce** and **Perch** are the exception in the other direction: both read
their palette at runtime and follow macOS's Light/Dark themselves, so on a dark
Mac they stay dark even under `flavor = "latte"`. Pin them to the flavor with
`haus.pounce.followSystemAppearance = false` /
`haus.perch.followSystemAppearance = false` — though if you set
`systemAppearance = "flavor"` above, macOS's polarity *is* the rice's, so those
two follow the flavor anyway and pinning them is only needed while macOS stays
unmanaged.

The generated [`minimal` desktop](#the-desktop) follows the flavor in every
part — field, mark, bloom and debug band. The three hand-made looks do not:
their pixels are already coloured dark. `style = "bold"` is generated but
follows your accent rather than the flavor.
</Aside>

## The desktop

The wallpaper is generated on your machine, not shipped as a picture:

```nix
haus.wallpaper.style = "minimal";
```

`minimal` is one flat colour out of your palette, the haus mark **⌂** at the
centre, and a very broad bloom in your accent behind it. That is the whole
design — there is no photograph to clash with a terminal in front of it, and
nothing that stops reading as a background once you have windows open.

Every part of it is a knob, and the defaults are the look above:

| | |
|---|---|
| `haus.wallpaper.depth` | how far in from the palette's outermost tone the field sits, `0`–`5`. `0` is our blackest black in a dark rice and our whitest white in a light one; `1` (the default) sits exactly one rung inside that in either polarity — `#191919` dark, `#e9e9e9` light. That is one step below the colour your terminal draws on in a dark rice, which is what keeps a whole screen of it reading as a wall rather than as a very large terminal window; in a light rice the canvas is already the lightest tone there is, so a step below it is the better end of the trade for a whole screen of near-white. `depth = 2` matches the terminal exactly in dark mode, `depth = 0` in light. `haus.wallpaper.background` overrides it with a literal hex. |
| `haus.wallpaper.mark.*` | `enable`, `size`, `weight`, `opacity`, `rise` (how far above centre it sits), and `color` — `muted`, `ink`, `accent`, or `spectrum`, which is the six-product conic sweep the ⌂ wears when you hover it on [hausfold.co](https://hausfold.co), held still. The shape is the real **U+2302**, traced off the outline the site renders, so the roof ends on the walls rather than overhanging them — the weight is the one thing that isn't the glyph's, at about half of it, since a stem that reads right in a line of type is heavy drawn a foot wide. |
| `haus.wallpaper.glow.*` | the bloom: `color` (your accent unless you say otherwise), `strength` as a percentage, and `spread` as a multiple of the long edge. |
| `haus.wallpaper.grain` | film grain, and the reason the bloom doesn't band — see below. |
| `haus.wallpaper.size` | the pixel size to render at. |

### Why it doesn't band

A soft gradient across two thousand pixels spends about ten of the 256 levels
an 8-bit PNG has, so it quantises into visible contour rings — the stepped look
a hand-made wallpaper picks up on the way out of an image editor. The rice
composes the field at **16 bits**, adds a couple of levels of grain, and only
then reduces to 8 — so the noise dithers the reduction instead of the reduction
drawing rings. `grain = 0` turns it off, and you should only do that with
`glow.enable = false` as well.

Measured at the defaults, since it's easier to state than to argue about —
distinct colours in the finished PNG, and what it costs, noise being the one
thing that doesn't compress:

| `grain` | colours | size | |
|---|---|---|---|
| `0` | 137 | 0.1 MB | rings, visibly |
| `0.004` | 193 | 1.1 MB | the floor worth using |
| `0.01` | 329 | 2.5 MB | the default |
| `0.02` | 625 | 4.2 MB | |

The other half is `size`. Set it to your display's **native pixel count**
(`system_profiler SPDisplaysDataType` prints it) and macOS has nothing left to
rescale; anything else is resampled, and resampling undoes the dither. macOS
also fills the screen and crops the overflow, so a picture of a different shape
than your display loses its top and bottom.

Preview any of this without rebuilding a Mac:

```sh
nix build github:hausfold/hausfold#wallpaper && open result
```

### The lock-edge band

Off by default:

```nix
haus.wallpaper.debug.enable = true;
```

It prints which revision of each family repo this machine was built from —
`haus`, `nebelung`, `pounce`, `perch`, `holt` by default, and
`haus.wallpaper.debug.inputs` picks the list. Small, dim, wide-tracked, bottom
left.

The placement is the point: it sits at exactly the inset a tiled window's
bottom-left corner lands on, read from the same gap numbers
[prowl](/guides/window-management/) writes into its config. So it is completely hidden the
moment anything is on screen, and only ever surfaces on a bare desktop.
`haus.wallpaper.debug.inset` overrides that in pixels.

## Obsidian vaults

Obsidian keeps themes and appearance settings **inside each vault**, so the rice
doesn't guess which folders are yours. List the vaults you want Nebelung to
manage as home-relative paths:

```nix
haus.hearth.obsidianVaults = [
  "Library/Mobile Documents/iCloud~md~obsidian/Documents/notes"
];
```

Then `haus rebuild`. For every listed vault, Hearth:

- copies the generated full Nebelung theme into
  `.obsidian/themes/Nebelung/`;
- selects Nebelung's appearance (dark today, regardless of
  `theme.flavor` — Obsidian is one of the places light mode does not yet
  reach); and
- disables the obsolete `nebelung` CSS snippet if it was enabled.

The rest of `appearance.json` is merged and preserved. A path is skipped with a
warning unless it already contains `.obsidian`, so a typo won't create an empty
lookalike vault. List multiple paths to keep several vaults in sync; the default
`[]` touches none.

## Apps you added yourself

Everything above covers the tools the rice installs — it owns their configs and
themes each one properly. Apps **you** put in your
[roster](/guides/adding-apps/#a-gui-app-with-a-launcher-key-the-roster) get the
same treatment automatically, as long as the name you keyed the entry under
matches a nebelung port:

```nix
haus.roster = {
  zed  = { key = "e"; name = "Zed";  appId = "dev.zed.Zed";     cask = "zed"; };
  warp = { key = "w"; name = "Warp"; appId = "dev.warp.Warp-Stable"; cask = "warp"; };
};
```

On the next `haus rebuild`, each one's Nebelung theme is written where that app
looks for themes — `~/.config/zed/themes/`, `~/.warp/themes/` — in your current
flavor, contrast and accent, and re-written whenever you change them. Nothing
else to wire.

The key is the **roster id**, not the display name: `zed`, not `zed-editor`. Set
`haus.theme.ports.enable = false` to turn the whole pass off.

### Which ones need a click

Dropping a theme file is enough for apps that read a fixed path. Plenty of
others — Xcode, Warp, OBS, JetBrains, Tabby — have no file interface for
*choosing* a theme; the file is put where they look, and the one-time pick stays
yours. A handful more (Slack, Raycast, qBittorrent) can't be installed by file
at all.

Rather than leave you to discover that months later wondering why an app still
looks stock, `haus doctor` tells you exactly where each one stands:

```
🌫  Nebelung theme
  ✓ gitui — themed (~/.config/gitui/theme.ron)
  ⓘ Xcode — placed at ~/Library/…/Catppuccin Mocha.xccolortheme — pick it in the app's settings
  ⓘ Slack — not installed — copy the comma-separated hex string → Slack ▸ Preferences ▸ Themes ▸ paste
```

A ✓ is live now. A ⓘ tells you the one move left. nebelung publishes which is
which per tool — the full table is in its
[ports documentation](https://github.com/hausfold/nebelung/blob/main/docs/ports.md).

<Aside type="note" title="Merges are reported, never applied">
Ports installed by merging into an existing config file (VS Code's
`settings.json`), or needing a compile step first (qBittorrent), are listed with
instructions but never written. Silently half-editing a config you own is worse
than telling you what to do.
</Aside>

## Why bake, not load at runtime?

Colours are generated at **build time** from a single source, not loaded from
loose theme files. That means the palette can never drift out of sync: change
nebelung, `nix flake update`, rebuild, and every tool gets the exact same new
values at once. No "I updated the terminal but forgot lazygit" surprises.

## Using nebelung outside the rice

nebelung is a standalone colour system — you can theme any tool without the rest
of nebelhaus. Two ways:

- **Copy a rendered theme.** Each tool's theme is generated into the flake's
  output tree; grab the file for your tool and point its config at it. See the
  [palette reference](/reference/palette/#using-it-in-your-own-tools) for the
  per-tool paths.
- **Consume the flake.** Add the input and reference the built output:

  ```nix
  inputs.nebelung.url = "github:hausfold/nebelung";
  # then: ${nebelung.packages.${system}.default}/<tool>/...
  ```

  The flake also exposes a raw `palette` attrset (`name → "#hex"`) for configs
  you generate yourself.

## Tuning the palette itself

Want a different fog? The palette is computed in
[OKLCH](https://oklch.com/) space from a handful of knobs in nebelung's
`scripts/generate-palette.mjs` — the grey's hue and chroma, how much the accents
are calmed, which Catppuccin flavor to strip, and how far to push the contrast —
then rebuilt with `./build.sh`. That's a nebelung-repo
change rather than a host-file one; the [palette reference](/reference/palette/#tuning-the-palette)
covers the details.
