nebelhaus ships a *complete* opinion — system and shell, already wired. So
"customizing" isn't reassembling anything; it's turning a handful of dials. This
page is the map of those dials and the thinking behind the loudest defaults.

## The one file you edit

There are two halves to your setup, and they stay cleanly apart:

- **The desktop** (`github:hausfold/haus`) — the generic, no-identity system.
  You *never* edit this to use it. It updates upstream; you pull it when you like.
- **Your config** (`~/.config/nix`) — a ~18-line flake that imports the desktop,
  plus **one host file** where *you* live:
  `hosts/<hostname>/default.nix`.

That host file is where every tweak on this page goes. Open it instantly:

```sh
haus edit
```

It's a plain nix-darwin module — whatever you write merges with what the desktop
already declares. Change something, then:

```sh
haus rebuild    # builds first; a broken config never activates
```

<Aside type="tip" title="Why the split matters">
Because *your* stuff and *the desktop* are separate repos, `nix flake update
nebelhaus` (or `haus update`) pulls new fog without ever touching your identity,
apps, or overrides. Your machine stays yours; the desktop stays upstream. Keep
personal things in your host file — never in the desktop repo itself.
</Aside>

## The named-workspace idea

The single biggest opinion in nebelhaus is how windows are arranged, so it's
worth saying out loud: **the things you live in get workspaces of their own, and
one key takes you there.**

Instead of alt-tabbing through a soup of windows, you build muscle memory: the
terminal is always <kbd>⇪</kbd> <kbd>T</kbd>, the browser is always
<kbd>⇪</kbd> <kbd>B</kbd>, Slack is always <kbd>⇪</kbd> <kbd>S</kbd>. The app is
launched if it isn't running, focused if it is, and it lands on *its* workspace
every time. Your hands stop negotiating with the window manager.

That scheme comes from **two keyed maps that pair up**: `haus.roster` says
what the machine has and which letter launches it, and `haus.workspaces`
says which workspaces exist and which roster apps live on each. Keeping
membership on the *workspace* is what lets one workspace hold several apps — a
`comms` space with Slack, Mail and Messages — instead of forcing one app per
workspace. Both are keyed attribute sets, so they compose cleanly across your
host file, app packs, and pounce-generated package modules. A few things worth
internalizing:

- **Letters are yours, digits are scratch.** Workspaces `1`–`4` are generic
  scratch space and always exist; everything else (`T`, `B`, `S`, `comms`…) is
  something you named.
- **Focus vs. throw.** Tap <kbd>⇪</kbd> then an *app's* letter to *go there* —
  it launches or focuses the app and lands you on whatever workspace it belongs
  to. <kbd>⇪</kbd> then <kbd>⇧</kbd> and a *workspace's* key *throws the current
  window* there instead, and follows it. (For a workspace holding one app the
  two keys are usually the same letter, which is why they feel like one binding.)
- **Launcher-only apps exist.** A roster entry that no workspace lists just
  launches in place — no dedicated workspace, no pill. Handy for a password
  manager or a calculator.
- **Floating apps exist too.** `float = true` on a roster entry keeps that app's
  windows out of the tiling entirely, for a picker or status window that would
  otherwise reflow the whole workspace every time it opens. It needs the entry's
  `appId` — without one it is silently inert and only warns during a rebuild.

Adding your own is a one-liner — see [Adding apps & tools](/guides/adding-apps/)
for the recipe and [Window management](/guides/window-management/) for the full
binding set.

## The cookbook

Every knob below is a `haus.*` option (or a plain nix-darwin one) you set in
your host file. This is the tour; the exhaustive list with types and defaults is
the [options reference](/reference/options/).

Or don't look any of it up. The desktop installs a skill that teaches Claude Code
this whole surface — generated from the revision you're pinned to — so you can
ask in plain words instead: [Changing your Mac with an
agent](/guides/ai-agent/).

Or read the surface straight out of your own config. A fresh install drops a
`hosts/<host>/options.nix` beside your host file — every `haus.*` option at
its default, a sentence each, **all commented out**. Uncomment what you want,
delete what you'll never touch; you find out a knob exists by reading the file you
already edit. It's rendered from the build you're actually running, so it can't
advertise an option your machine doesn't have — the desktop-side twin of pounce's
`pounce config init`. If you've edited your copy, a refresh writes
`options.nix.new` beside it rather than overwriting your work.

```sh
haus options    # refresh it against the current desktop (--force overwrites yours)
```

<Aside type="note" title="Scaffolded, not active">
Nothing in that file does anything until you uncomment a line *and* `import` it —
`haus options` prints the `imports = [ ./options.nix ];` line to add if your host
file is missing it. Commented-out is deliberate, for two separate reasons. A
spelled-out default **collides** with a preset rather than beating it — import
order carries no priority, so `extraModules = [ nebelhaus.presets.large-print ]`
would fail on `haus.ui.scale` with a conflict, not pick a winner. And against
the desktop's own `mkDefault`s a plain restatement *does* win, permanently, freezing
that value against any future retuning upstream.
</Aside>

For a one-off change, you can skip the editor entirely. `haus set` writes and
stages a small ordinary Nix module per `<path> <value>` pair under
`hosts/<host>/settings/`, type-checks them, and rebuilds once. Staging is what
makes a new file visible to a git-backed flake; the command does not commit or
push your config repo.

```sh
haus set theme.accent teal
haus get theme.accent        # teal
haus reset theme.accent      # remove the override; inherit the desktop/preset again
```

A path may go *inside* an option — `haus set sill.items.aiUsage true` switches
one pill, `haus set displays.internal.uiScale larger-text` scales one screen.
Prefer that to naming the whole attribute set: the overlay is `mkForce`, so
`haus set sill.items '{"aiUsage":true}'` would send every pill you didn't name
back to its default. (If a key *inside* it is already in the overlay, the
whole-set form is refused outright instead — the silent reset only happens from
a clean overlay.)

Only `haus.*` options cross this writable boundary (the prefix is optional
on the command line). `haus unset <path> […]` explicitly writes `null` for
nullable options; `haus reset <path> […]` removes the generated overrides. Both
take a list, and — like `haus set`'s pairs — apply it all-or-nothing in a single
rebuild, so undoing a two-option change is one command too. See [the haus CLI
reference](/reference/haus/#the-writable-settings-overlay) for the exact model.

### Identity

```nix
haus.git.name = "Ada Lovelace";
haus.git.email = "ada@example.com";
haus.git.signingKey = "6F7BD6F43A7C1420";  # "" to disable commit signing
haus.git.org = "analytical-engine";        # the GitHub owner your work lives under
```

`org` is the odd one out — not who you are, but where you work. Today only
gh-dash reads it: it fills `⌘G`'s PR tabs with that owner's open, green, red and
just-shipped work, so an org rename is one word here rather than one per tab. On
its own it does nothing — the overlay is opt-in, so set
`haus.hearth.ghDash.enable = true` alongside it, and keep the Git pack on
(`haus.developer.git.enable`), which is what installs `gh`; the two are asserted
together, so the overlay without the pack fails the build. See [Your review
queue](/guides/the-shell/#your-review-queue).

### The look

```nix
haus.theme.accent = "sapphire";     # any of 14 Catppuccin accent names
haus.wallpaper.style = "minimal";   # the default — none | minimal | orbits | constellation | flow | bold
```

`accent` recolours lazygit, fzf, yazi/Glow, and the browser accent. Full palette
on [Theming & accents](/guides/theming/).

`minimal` is the wallpaper the desktop generates for you, and the one it wears unless
you say otherwise: a flat field in your
palette, the haus mark ⌂ at its centre, and a bloom in your accent. Set
`style = "none"` to keep the wallpaper you already have. It has a
room of its own — the field's depth, the mark's size and colour, the bloom, the
grain, and an off-by-default band of this machine's lock edges — under
[`haus.wallpaper.*`](/reference/options/#hauswallpaperstyle) and on
[Theming & accents](/guides/theming/#the-desktop).

### The shell

```nix
haus.hearth.editor = "nvim";                # the ONE editor: $EDITOR + every "open in editor" action
haus.hearth.hijackFileAssociations = false; # make that editor the default file opener
```

More on each in [The shell](/guides/the-shell/).

### Apps, tiling & the launcher

```nix
haus.roster.slack = { /* one keyed roster entry — see Adding apps */ };
haus.prowl.enable = true;    # false: no tiling, no Caps-Lock remap
haus.pounce.enable = true;   # false: no ⌘Space palette
haus.pounce.signingIdentity =      # sign it and its Accessibility grant survives rebuilds;
  "Developer ID Application: Ada Lovelace (ABCDE12345)";   # "" (the default) runs it unsigned
```

### The bar

```nix
haus.sill.enable = true;              # false: keep the native macOS menu bar
haus.sill.items.elgato = true;        # opt-in extras: agents | aiUsage | github |
                                           # cpu | memory | volume | calendar |
                                           # caffeinate | elgato | harvest
```

The bar's optional plugins are personal — an Elgato Key Light toggle, a Harvest
timer, an agents pill — off unless you ask. See [The bar](/guides/the-bar/).

### The first-run tour

The built-in tour teaches nebelhaus's four core moves. A shared desktop can replace
that lap with its own instructions while staying data-only:

```nix
haus.tour.steps = [
  {
    hint = "Press {palette}, type tour, then hit ↵";
    detect = "palette";
  }
  {
    hint = "Move to another workspace";
    detect = "workspace";
  }
];
```

Steps run in order and advance from signals the desktop already emits — `launch`,
`workspace`, `navigate`, `resize`, or `palette` — rather than by logging keys.
The first four need prowl; `palette` needs Pounce **and a palette key actually
bound** (`keys.palette = "none"` warns as loudly as `pounce.enable = false`). A
left-click skips the current step, and the module warns during a rebuild if a
step depends on a room you disabled — though all three of those warnings live
inside sill's own module, so a desktop that turns the bar off gets none of them.

Leave `tour.steps` at its default `null` to keep the built-in tour. An **empty
list** is a type error rather than "no tour" — the off switch is
`tour.enable = false`.

Write keys as the placeholders `{palette}`, `{leader}` and `{leaderName}` rather
than a literal chord: they expand to what *that* machine resolved, so a tour you
share still names the right keys on a desktop that moved `keys.palette`. A hardcoded
`⌘Space` would be wrong there — and wrong invisibly, since the author never sees
the consumer's bar. A misspelled placeholder renders as typed, and the rebuild
warns and names it.

<Aside type="caution" title="Tour with prowl off">
The built-in tour is leader moves plus the palette, so turning prowl off leaves
it nothing to teach: `tour.enable` on a `prowl.enable = false` desktop draws no pill
at all unless you author `tour.steps` yourself. The `everyday` preset does exactly
that — one step, the launcher.
</Aside>

### Homebrew behaviour

```nix
haus.homebrew.cleanup = "none";    # none | uninstall | zap — how rebuild treats undeclared apps
haus.homebrew.autoUpdate = false;  # brew update before each rebuild
haus.homebrew.upgrade = false;     # upgrade outdated packages each rebuild
```

`cleanup` defaults to `"none"` so nothing you installed by hand is ever removed.
Set it to `"zap"` if you want a *fully* declarative machine where undeclared
casks get uninstalled on rebuild.

These are policy knobs only — the apps themselves belong in `haus.roster`,
including the ones you don't want a launcher key for (just omit `key`). See
[Adding apps & tools](/guides/adding-apps/#one-list-hausroster-and-one-that-pairs-with-it).

<Aside type="tip" title="Keeping casks current">
`autoUpdate` and `upgrade` are **off by default** so a rebuild is
reproducible — it installs a cask once, then pins whatever version brew first
laid down. That's why a cask app can sit on an old version even though your
config is fully synced: a rebuild keeps it *installed*, not *current*. To
pick up new releases of a fast-moving cask, either upgrade it on demand —

```sh
brew upgrade --cask zen
```

— or set both knobs to `true` so every rebuild tracks upstream latest:

```nix
haus.homebrew.autoUpdate = true;  # brew update first, so it sees new versions
haus.homebrew.upgrade = true;     # then upgrade outdated casks
```

The trade-off is the flip side of reproducibility: a rebuild may now upgrade
**all** your casks at once, so two rebuilds days apart can land different app
versions. Prefer per-host: set these in your host file, not the desktop default,
so the rest of the family keeps deterministic rebuilds.
</Aside>

## Turning rooms off

Every room you can see has a switch:

| Room | Option | Off means |
|---|---|---|
| prowl (tiling) | `haus.prowl.enable = false` | No AeroSpace, no leader key |
| sill (bar) | `haus.sill.enable = false` | The native menu bar stays |
| pounce (launcher) | `haus.pounce.enable = false` | No ⌘Space palette |
| perch (notch shelf) | `haus.perch.enable = false` | No shelf. The `/Applications/Perch.app` an activation copied in stays — delete it by hand |
| hush (quiet switch) | `haus.hush.enable = false` | No bar pill, palette command or `hush` CLI |
| collar (Touch ID sudo) | `haus.collar.enable = false` | The stock password prompt everywhere, rebuilds included |
| the developer pack | `haus.developer.enable = false` | No language toolchains, git tooling or agent CLIs. `.git`, `.toolbelt`, `.agents` and `.languages` take one piece out at a time |
| apps (the desktop's [picks](/guides/adding-apps/#the-apps-the-rice-picks-for-you)) | `haus.apps.videoPlayer.enable = false` | No IINA; videos keep whatever handler they have |

**pounce** doesn't hand its key back on the way out: turning it off does not
return `⌘Space` to Spotlight, because that shortcut was disabled by a one-way
`defaults write` and nothing re-enables it. Re-bind it in System Settings ▸
Keyboard ▸ Keyboard Shortcuts. **hush** is the mirror image — it *binds* a Do
Not Disturb chord onto a shortcut macOS ships disabled, so switching the room
off leaves a spare binding rather than removing one.

If what you actually want is the tiler **without** its keyboard claims, don't turn
the room off — set `haus.keys.leader = "none"` and
`haus.keys.windowNav = "none"` instead. prowl keeps tiling and Caps-Lock stays
Caps-Lock. See [rebinding](/guides/window-management/#not-fond-of-these-keys).

**den** (system + Homebrew) and **hearth** (shell) are the foundation the rest
sits on and have no switch; of the rooms you can *see*, all six do. Everything
in the table comes out independently, and the others keep working — the desktop
degrades gracefully.

## Presets: start from someone else's desktop

A **preset** is a data-only desktop — a file whose only top-level key is
`haus`. No `pkgs`, no `lib`, no activation scripts, so it can't reach outside
the option surface and you can read one in a minute and know the worst it can do.
Import one alongside your host file:

```nix
darwinConfigurations.myhost = nebelhaus.mkNebelhaus {
  username = "ada";
  hostname = "myhost";
  host = ./hosts/myhost;
  extraModules = [ nebelhaus.presets.everyday ];
};
```

Your host file can override anything a preset sets — but not by being imported
*after* it. Import order carries no priority in Nix's module system: an option
the preset leaves alone is yours to set plainly; an option it also sets to a
*different* value is a *conflict*, not a silent win, until you reach for
`lib.mkForce`. (Setting one to the value it already holds is fine — identical
definitions merge, so restating a preset's own choice costs you nothing.)

```nix
{ lib, ... }:                              # add lib to your host's args
{
  haus.ui.scale = lib.mkForce 1.0;    # large-print sets this — force to win
}
```

| Preset | For |
|---|---|
| `full` | the whole desktop: bar, tiling, palette, developer pack. The default. |
| `minimal` | just the themed shell — no bar, no tiling, no palette. Still a developer machine. |
| `everyday` | the inverse: a Mac for someone who doesn't write code. No developer pack, and `prowl.enable = false` — so no tiling either, not just no Caps-Lock remap. |
| `large-print` | bigger and sharper — the desktop UI and whole display, plus the high-contrast palette and macOS's own contrast lift. |

The first three are whole desktops; pick one. **`large-print` is a layer** — it
describes seeing rather than the person, so it stacks:

```nix
extraModules = [ nebelhaus.presets.everyday nebelhaus.presets.large-print ];
```

It uses two complementary size controls. `ui.scale = 1.4` moves the terminal
font, the whole command palette, the menu bar's type, the Dock icons, Finder's
sidebar rows and the tiling gaps together — pin any single one afterwards and
yours wins. (One thing inside the desktop it does *not* move: the perch shelf,
which takes its size from the screen rather than from you.)
`displays.main.uiScale = "larger-text"` moves the current main display one step
toward larger text, which makes **everything** bigger, including third-party apps
the desktop knows nothing about. The trade-off is less desktop space.

Note that the two **multiply**: a larger-text display leaves you fewer points of
desktop, and `ui.scale` asks for bigger points inside it. That's the intended
effect — it's just a bigger jump than either alone.

For per-display control, add a UUID-specific setting in your host file; it wins
over the preset's broad `main` selector. `hausdisp list` prints the persistent
UUIDs of the displays currently attached.

One size limit remains, and it's macOS's rather than the desktop's: **the menu bar's
height.** Sill is 36pt tall with 28pt pills so the pills sit inside the 32pt band
that macOS's own menu-bar hover-reveal covers — taller pills poke out below it.
There is no menu-bar-size setting on macOS to delegate to. So the bar's *type*
follows `ui.scale` up to 1.25× and then stops, and prowl gives the bar a little
extra room against the tiled windows as it grows. Making the whole bar bigger is
what `displays.*.uiScale` is for: it changes what a point *means*, which is the
only thing that band responds to.

The preset also doesn't change an app's own font preference or macOS's separate
Dynamic Type text-size setting; display scaling is the system-wide lever that
works.

Want to make one for other people? [Sharing a desktop](/guides/sharing-a-rice/)
covers the data-only boundary, `checkRice`, composition testing, and the
smallest useful publishing shape.

## Overriding macOS defaults

The desktop sets Dock, Finder, trackpad, and keyboard defaults — but every one of
them is a *soft* default you can beat by just setting the same key with a plain
value in your host file:

```nix
# Desktop hides the Dock and puts it on the bottom; put it on the left, always shown:
system.defaults.dock.autohide = false;
system.defaults.dock.orientation = "left";
```

Anything under [`system.defaults`](https://nix-darwin.github.io/nix-darwin/manual/)
is fair game. Your plain value wins over the desktop's default.

<Aside type="note" title="Four exceptions">
Two menu-bar keys track whether the bar (sill) is on, so the desktop sets them
plainly rather than as `mkDefault`s:

- **`_HIHideMenuBar`** — the auto-hide, a typed nix-darwin option. Setting it in
  your host file is a **conflicting definition**: the evaluation fails rather
  than one value winning. That's the good outcome — `mkForce`-ing it off while
  sill is on gets you a bar and a menu bar fighting for the same strip of pixels.
- **`NSGlobalDomain.SLSMenuBarUseBlurredAppearance`** — System Settings ▸ Menu
  Bar ▸ "Show menu bar background". Tahoe's Liquid Glass made the hidden menu
  bar's hover-reveal translucent, so Sill showed straight through it; the desktop
  forces it opaque again. It goes through `CustomUserPreferences`, so it is
  rewritten on every activation rather than merged: flip it in System Settings
  and the next rebuild flips it back.

And one macOS ignores outright: **`NSGlobalDomain.AppleInterfaceStyle`** (Light/
Dark). It is a typed nix-darwin option, and on macOS 26 writing it does nothing
in either direction — the key is where macOS *mirrors* the appearance it's
showing, not a lever, so even a plist read-back agrees with you while nothing
changes. `haus diff` flags it. Use
[`haus.theme.systemAppearance`](/reference/options/#hausthemesystemappearance)
instead.

And one that works but not the way it reads: **`power.sleep.computer`** and its
neighbours (nix-darwin's own, not `haus.*`). They run `systemsetup`, which has
no way to say *which* power source you mean — on macOS 26 one of them wrote the
**charger** profile while the Mac was running on **battery**, and nix-darwin
throws the output away, so nothing says so. Use
[`haus.power.*`](/reference/options/#hauspowercomputersleepbattery) instead: it says `battery` and
`charger` separately, which is the only thing a laptop actually wants.
</Aside>

## Secrets & private things

Anything sensitive — API keys, tokens, your app list if you'd rather it stay
private — belongs in your host file (which is *your* repo). The secret **values**
belong nowhere on disk at all, and the desktop ships
[secretspec](https://secretspec.dev) to keep them there:

```sh
secretspec set SOME_API_KEY    # once — into your macOS login keychain
secretspec run -- some-tool    # injected as an env var, for that process only
```

A committable `secretspec.toml` declares *which* secrets a project needs — names
and descriptions, never values — and `haus.secrets.provider` (default `keyring`,
the login keychain) decides where the values live. Point it at a cloud vault
instead and they follow you between machines. On a fresh Mac, `secretspec check`
lists exactly what still needs entering, and `haus doctor` runs the same check.

Nothing lands in the world-readable Nix store, and there is no plaintext dotfile
to remember to keep out of git.

<Aside type="tip" title="Publishing it instead? Put gitleaks in front">
If you'd rather share your host repo than keep it private, add a
[gitleaks](https://github.com/gitleaks/gitleaks) pre-commit hook so a stray key
never gets to *be* a commit:

```sh
cd ~/.config/nix
printf '#!/bin/sh\nexec gitleaks git --pre-commit --staged --redact --verbose\n' \
  > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Add `gitleaks` to `home.packages` so the hook has something to run. It exits
non-zero on a hit and stops the commit; `git commit --no-verify` overrides it
when you're sure. Scan the history you already have *before* you flip the repo
public — plain `gitleaks git` walks every commit, and deleting the line later
doesn't unpublish the key, so rotate anything it finds.
</Aside>

<Aside type="tip" title="Wrong repo?">
Changing a *color*? That's the [nebelung](/reference/palette/) palette, a
different repo. Changing the desktop's *shared* behaviour for everyone (not just
your machine)? That's the nebelhaus repo — see
[Contributing](/internals/contributing/). Personalizing *your* Mac? You're in
the right place: your host file.
</Aside>
