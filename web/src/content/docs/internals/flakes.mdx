nebelhaus is built on [Nix flakes](https://nixos.org/). You don't need to
understand Nix deeply to use the desktop, but knowing how the pieces fit makes the
`update` / `rebuild` model click — and it's essential if you want to
[contribute](/internals/contributing/).

## Your config is a thin consumer

The installer scaffolds `~/.config/nix` as a **thin consumer** of the desktop. Its
`flake.nix` imports nebelhaus as an input and calls the `mkNebelhaus` builder:

```nix
{
  inputs.nebelhaus.url = "github:hausfold/haus";

  outputs = { nebelhaus, ... }: {
    darwinConfigurations.<hostname> = nebelhaus.mkNebelhaus {
      username = "<user>";
      hostname = "<hostname>";
      host = ./hosts/<hostname>;
    };
  };
}
```

All your personal choices live in `hosts/<hostname>/default.nix` — your
[options](/reference/options/), your app roster, your casks. The desktop stays
upstream; you never edit it directly.

Three other things sit in that host directory: `options.nix`, the whole
catalogue of `haus.*` options at their defaults regenerated from the build you
are running, and `packages/` and `settings/`, both auto-imported alongside
`default.nix` — that is where `haus set` and Pounce's *Install App* write. There
is no second store of state anywhere; the machine writes the same Nix you do.

## The mkNebelhaus builder

`mkNebelhaus` is the desktop's entry point. Given a username, hostname, and host
file, it returns a full nix-darwin `darwinSystem` with every room wired up:

```nix
nebelhaus.mkNebelhaus {
  username = "ada";
  hostname = "fog";
  host = ./hosts/fog;          # your identity + choices
  system = "aarch64-darwin";   # Apple Silicon only
  extraModules = [ ];          # extra nix-darwin modules, optional
}
```

Only `username` and `hostname` are required — `host` defaults to the repo's
example. It composes the whole house: 19 module imports covering 35 `haus.*`
namespaces, `den`, `theme`, `hearth`, `prowl`, `sill`, `collar`, `pounce`,
`perch`, `hush`, `secrets`, `workspaces`, `roster`, `displays`, `wallpaper`,
`snippets` and `apps` ([the picks the desktop makes for
you](/guides/adding-apps/#the-apps-the-rice-picks-for-you)) among them — and
layers in home-manager, the [nebelung](/reference/palette/) theme, and the
[pounce](/guides/pounce/) app.

**Eight** modules are exported individually under `darwinModules` (`den`,
`hearth`, `prowl`, `sill`, `collar`, `pounce`, `hush`, `secrets`, plus `default`
for the lot). Everything else — `theme`, `perch`, `apps`, `roster`,
`workspaces`, `displays`, `wallpaper`, `snippets` — rides along only with the
full house. ⚠️ Reach for an individual export only with `mkNebelhaus` still
around it: a module declares no `haus.*` options of its own (they all live in
`modules/options-modules.nix`, imported by `modules/default.nix`) and takes
`username` from the builder's `specialArgs`, so on its own it does not
evaluate.

## The inputs

The desktop flake pulls together nine:

- `nixpkgs` (unstable) — the package set
- `nix-darwin` — macOS system modules
- `home-manager` — your user environment
- `catppuccin` — the theme framework
- `nebelung` — the silver-mist palette (a family input)
- `pounce` — the launcher app (a family input)
- `perch` — the notch file shelf (a family input). ⚠️ The input carries no
  `ref`, so it tracks perch's default branch like every other one; what gets
  *built* is perch's CI-built, notarized release zip, because **perch's own**
  flake pins that zip in `nix/release.nix`. The pin is inside perch, not here.
- `holt` — the agent-worktree substrate. The builder applies its overlay
  unconditionally; den puts the CLI on your `PATH` only with
  `haus.agents.enable` (a family input)
- `nix-index-database` — for `nix-index` + `comma`

## Why pins mean "nothing changes until you say so"

Each input is recorded in `flake.lock` as an **exact commit hash**, not "latest".
That's what makes a rebuild reproducible — the same lock produces the same system
on any machine, any day.

The flip side, and the thing that surprises everyone: pushing a change to
nebelung or the desktop changes **nothing** on your machine until your `flake.lock`
is bumped to point at the new commit. A colour change therefore ripples like
this across the family:

![one colour change rippling down the chain: nebelung → pounce → nebelhaus → ~/.config/nix → your Mac, each lock pinning the exact commit of the one before](/media/ripple.webp?v=2)

`perch` and `holt` hang off the desktop directly rather than sitting on that line,
so a change in either is one shorter hop under the same rule.

<Aside type="tip" title="haus update does the ripple for you">
As an end user you never walk this by hand — `haus update` bumps your pin to the
latest nebelhaus (which already has its own inputs pinned), upgrades the
family's Homebrew-installed apps alongside it, prints what landed upstream, and
rebuilds (it rebuilds even when the pin didn't move). Family *contributors* use
the workshop's `bench ship` to ripple a change all the way down the chain; see
[Contributing](/internals/contributing/).
</Aside>

## Cold-boot safety

One subtlety worth knowing if you ever debug a login issue: Determinate Nix
lives on a separate APFS volume, and macOS sometimes tries to launch the desktop's
GUI agents (AeroSpace, SketchyBar, Pounce) before that volume mounts or before
the GUI event manager is ready. The desktop wraps **those three** in a small
`gui-wait` shim that polls for Dock/Finder/SystemUIServer readiness before
exec'ing — which is why your bar and tiling reliably come back after a reboot.
The shim is written *into* `~/Library/LaunchAgents` rather than referenced out
of `/nix/store`, which is the part that survives the unmounted volume, and it
gives up after 60 seconds and launches anyway: an unbounded wait meant quitting
Finder once left Pounce dead until the next reboot. The desktop's non-GUI agents —
`awake`, `hush-watcher`, `sleepwatcher` — are not wrapped.
