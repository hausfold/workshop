Want to hack on nebelhaus itself — the rice, the launcher, or the palette? This
page covers how the family is developed. (To just *use* nebelhaus, you never need
any of this — see [Keeping in sync](/guides/staying-in-sync/).)

## The workshop

The [workshop repo](https://github.com/hausfold/workshop) is a parent directory
that holds every family repo checked out side by side, plus a `bench` dev CLI (a
different tool from the [end-user `haus`](/reference/haus/)). Clone it and pull
the family:

```sh
git clone https://github.com/hausfold/workshop.git
cd workshop
./bench clone
```

You end up with nine independent git repos side by side — `nebelung/`,
`pounce/`, `perch/`, `holt/`, `haus/`, plus `trill/`, `hausfold.co/`,
`org-profile/` and `homebrew-tap/` — with the `bench` script sitting above them.

## Where a change goes

Each change belongs to exactly one repo. Start in the right one:

| Change | Repo |
|---|---|
| colours / palette / how a tool is themed | `nebelung` |
| the launcher app or a generic command | `pounce` |
| the notch file shelf (perch) | `perch` |
| macOS defaults, tiling, bar, shell, Touch ID | `haus` |
| how agent worktrees are made, parked or reaped | `holt` |
| the quiet notification banners | `trill` |
| this site | `web/`, inside the workshop |
| the Homebrew formula and cask | `homebrew-tap` — almost never; it is CI-owned and a hand-edit is overwritten |
| `bench` itself, and the cross-repo flow | the workshop |
| your own machine's apps / identity / secrets | `~/.config/nix` |

## The dev loop: try without pushing

The important trick is that you never have to push to *see* a change. The
workshop `bench try` builds your real machine config against the **local
checkouts** — uncommitted edits and all — using Nix `--override-input`:

```sh
# edit anything in nebelung/, pounce/, haus/…
./bench try            # does it build? (nothing pushed, nothing activated)
./bench try switch     # run it on this Mac (still nothing pushed)
```

When you're happy, commit in the repos you touched and let `bench ship` ripple
the change downstream — pushing each repo and bumping every `flake.lock` in
dependency order, so a colour change in nebelung reaches your Mac without you
hand-walking the [pin chain](/internals/flakes/#why-pins-mean-nothing-changes-until-you-say-so):

```sh
./bench ship
```

It refuses a dirty tree on purpose — commit messages are yours, lock bumps are
its — fast-forwards every checkout from origin *before* computing anything (a
lock bumped off a stale `main` pins the pre-merge commit and reports success),
and re-reads each lock afterwards rather than trusting the ripple moved.

`./bench status` opens with **what this Mac is actually running** — the pinned
build, or the local branches a `try switch` put on it — then every repo's git
state and every stale lock edge at a glance. A lock can also be **off-main**:
pinned at a rev that isn't on that repo's `main`, which is what a `nix flake
update` run inside an open PR leaves behind. It resolves fine until the branch
is deleted on merge, and then the downstream repo can't fetch its input at all —
so land the upstream PR first, then ship. `./bench rebuild` is always the way
back to the pinned build.

## Parallel agents & worktrees

nebelhaus is built to be hacked on by several coding agents at once — Claude
Code, Codex or OpenCode, whichever `haus.agents.default` names. Each runs in its
own **git worktree**, an isolated checkout on a `worktree-<name>` branch living
under `~/.cache/claude-worktrees/<repo>/<name>` (the path name is historical, not
a claim about the client), so agents never yank the branch out from under each
other. That whole mechanism (spawning with `Super a`, never losing work when a
pane closes, resuming a parked session, the statusline HUD) is
[`holt`](/guides/claude-agents/), which the rice ships, and it works for any
repo.
Three things matter specifically when the repo is a *family* one:

- **`bench try` is worktree-aware.** Run it from inside a worktree and that repo's
  flake override points at *your branch* instead of the main checkout — so an
  agent can prove its branch builds before anyone merges it. It substitutes one
  lane, and only for a repo in `FAMILY`: from a *workshop* worktree it overrides
  nothing at all, which is the whole reason the `holt child` recipe below exists.
  When a change spans repos, **`bench try lane`** builds your lane together with
  every `holt child` lane spawned from the same pane, in one rebuild, no PR
  needed — same who-not-where activation gate as a plain `try switch`.
- **`bench try switch` works from a worktree too** — that's how you feel ONE
  unmerged branch, which [try-batch](#feel-testing-the-whole-pr-queue-try-batch)
  can't do (it always combines the whole open-PR queue, and never sees
  uncommitted work). The gate is on **who, not where**: an AI agent is refused a
  worktree switch — activation is machine-wide and serial, so parallel agents
  would silently overwrite each other — while a person at the keyboard just runs
  it. An agent that's been asked to activate anyway sets `BENCH_AGENT_SWITCH=1`.
  Every switch leaves a receipt `bench status` reads back, so the machine can't
  quietly stay on a branch nobody remembers; `bench rebuild` returns to pinned.
- **Land work through a PR — never a push or local merge into `main`.** Parallel
  agents pushing straight to `main` clobber each other; a PR is conflict-detected
  and atomic. Push the branch, open a PR with a **What / Why / Verify / Watch-out**
  body, and merge it from GitHub. `bench status` lists every agent worktree and
  unmerged `worktree-*` branch so nothing rots silently.

Working from the workshop on a task that belongs to a *sub*-repo? Resolve the
workshop's main checkout from Git, then make the child worktree — this works no
matter where you cloned the workshop:

```sh
workshop_root="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"
cd "$(holt child "$workshop_root/nebelung")" # replace nebelung with the repo you need
```

That registers the child so its PR shows in the statusline, which a raw
`git worktree add` would not.

## Feel-testing the whole PR queue (try-batch)

Activating a Mac is **serial** — one `darwin-rebuild switch` is one machine state
— so with a stack of PRs waiting you can only feel-test one at a time. The
tempting shortcut is to merge them all to `main` first, then rebuild and tick them
off — but now unverified code is on `main` before you've felt it.

`bench try-batch` inverts that. For each repo it builds a throwaway integration
tree (the committed `main` plus every open PR merged in), overrides the flake at
those trees, and builds — or activates — the whole queue in **one** rebuild,
`main` untouched:

```sh
./bench try-batch            # build every open PR together; prints a tick-off checklist
./bench try-batch switch     # …and activate the combined tree on this Mac
```

Verify each PR (its body carries the Verify steps), then merge only the ones that
pass and leave the rest open. This is test-then-merge, not merge-then-test.

<Aside type="caution" title="Read the dropped list under the checklist">
It needs `gh`, and it **excludes** any PR that conflicts with the batch or whose
head branch isn't on origin — those are named in a footer beneath the checklist.
Tick the checklist off without reading that footer and you will believe you felt
a PR the batch never built. It also takes optional repo arguments
(`./bench try-batch switch pounce nebelung`).
</Aside>

## Feel-testing a zellij edit (zscratch)

One class of rice change escapes the ripple entirely. A freshly-built plugin
`.wasm`, a candidate zellij binary, or a layout change to tabs that already
exist **cannot hot-reload** — a running server caches plugin wasm in memory for
its whole lifetime — so seeing one means restarting the zellij server yourself,
which costs you every open tab. The rice ships **`zscratch`** for exactly this.
It renders your candidate over a copy of your live `~/.config/zellij` into a temp
config dir and boots a throwaway session in its **own Ghostty window**, so your
working multiplexer is untouched:

```sh
zscratch --config config.kdl             # try a candidate config.kdl
zscratch --layout my-layout.kdl          # …or a layout
zscratch --theme  nebelung.kdl           # …or a theme
zscratch --plugin tab-bar=tab-bar.wasm   # …or swap a freshly-built plugin
zscratch --bin /path/to/zellij           # …or a binary-level zellij patch
zscratch clean                           # kill the scratch session + temp dir
```

Feel it there; the real `bench try switch` happens once, at the end, already
knowing it works — and that activation costs you nothing, because zellij watches
its config and applies a new `config.kdl` to the *running* server in about a
second. Tabs, panes and live agent sessions stay exactly where they are; there is
nothing to press afterwards.

That only works because hearth installs `~/.config/zellij/config.kdl` as a real
file with a current mtime (`home.activation.zellijLiveConfig`) rather than as a
home-manager symlink. zellij decides "changed" from the file's mtime, and every
`/nix/store` file carries mtime = epoch 1 — so a symlinked config makes each
rebuild look *older* than what zellij already parsed, and nothing reloads at all.
That single stat is why a rebuild used to mean tearing the whole session down.
Note the treatment stops at that one file: `themes/nebelung.kdl` is still an
ordinary store symlink, so a theme edit carries the epoch-1 mtime and does *not*
hot-reload — which is what `zscratch --theme` is for.

Plugin `.wasm`, a patched zellij binary, and layout changes to tabs that already
exist still cannot hot-reload — a running server caches plugin wasm in memory for
its lifetime. That is exactly the gap `zscratch` fills, which is why it is the
tool above and not an afterthought.

## The whole life of a change

```
hack ──► test ──► assure ──► PR ──► batch-test ──► merge ──► try switch ──► ship ──► release
```

1. **hack** — edit in place, or let `Super a` agents draft on `worktree-*`
   branches in parallel; the main checkouts never move.
2. **test** — `./bench try` builds your real machine against the local checkouts
   (from inside a worktree, against *that* branch). `./bench try switch` activates
   it, from a worktree too — that's how one branch gets felt on its own.
3. **assure** — before the PR exists, an agent hands `git diff main...HEAD` to a
   **clean-context subagent** that has read nothing but that diff and the edited
   repo's `AGENTS.md`. The session that wrote the change is the worst reviewer of
   it, so this pass looks for what only bites after merge: a change sitting in the
   wrong repo, docs left stale by a renamed option or keybind, a breaking rename
   split across two PRs, a colliding hotkey. It's advisory — anything serious gets
   fixed before the PR opens, the rest goes into the PR's **Watch out** block.
4. **PR** — push the branch and open a PR against `main`; never push to or
   `git merge` into `main` directly.
5. **batch-test** — `./bench try-batch` feels the whole open-PR queue in one
   rebuild, `main` untouched — so you verify *before* landing anything.
6. **merge** — merge the PRs that passed (on GitHub, or `gh pr merge`); leave the
   rest open.
7. **try switch** — on `main`, now that it holds the work.
8. **ship** — `./bench ship` pushes upstream→downstream, rippling every
   `flake.lock` in dependency order.
9. **release** — `./bench release <repo>`; CI does the rest, and the command
   waits with you while it happens. Four repos are releasable: **pounce**
   (GitHub release + Homebrew *formula* bump), **perch** (Homebrew *cask* bump,
   plus a commit of perch's own `nix/release.nix` back to the perch repo — the
   rice's flake pin only moves on the next `bench ship`), **haus** (the tag
   becomes what `nebelhaus.com/init.sh` serves to new installs), and **holt**
   (five SDKs, to npm, PyPI, crates.io, SwiftPM and the Go proxy).

<Aside type="note" title="Releases ride tags">
Versions are date-based (CalVer). `bench release <repo>` stamps today's date —
`YYYY.MM.DD`, or `YYYY.MM.DD-N` on a same-day repeat — into the repo's version
source, commits it, and tags `v<date>`; passing a version to a CalVer repo is
*refused*. CI then publishes the GitHub release, and for the two app repos bumps
the formula and the cask — haus's run has no tap job at all, and holt's publishes
SDKs. No number is typed by hand, and you never hand-edit the formula's url/sha.
It also wants a clean tree and no unpushed commits before it starts. And because
the installer serves the latest **rice** release, user-visible rice changes
aren't really "out" until `bench release haus` tags one.

**holt is the exception**, and it's forced: `bench release holt 0.2.0` takes a
**semver** argument and refuses to run without one. Its five SDKs publish to
registries where a number, once published, can never be withdrawn — so the
version is a compatibility contract, not a date, and all five share it.
</Aside>

There's exactly **one** workflow to watch — each repo's `release`, one to three
jobs for the app repos and eight for holt, whose SDKs publish separately — and
`bench release` draws them live rather than handing you a URL:

```
   ✓  build + publish release           2m 41s
   ⠹  bump hausfold/homebrew-tap           9s
```

It exits non-zero if the run goes red (with the `gh run view --log-failed` to
run), and on green it fast-forwards your checkout — which is the actual reason
it blocks. perch's run commits `nix/release.nix` back to the repo,
so a command that returned at the tag push would leave you a checkout behind
origin and a `bench ship` that ripples a rev CI is about to supersede. Pass
`--ship` to ripple that new lock edge downstream in the same breath; without it
you get the nudge and decide yourself, since `ship` touches the whole family.

Each repo carries its own `AGENTS.md` with the deep rules for that boundary —
start there when working inside one. It's the one instruction body every client
reads (Codex, OpenCode, Cursor, Zed, Copilot and anything else that speaks
[agents.md](https://agents.md)); the `CLAUDE.md` beside it imports that file with
`@AGENTS.md` and adds nothing but Claude-specific wiring, because Claude Code
reads only its own filename. Rules go in `AGENTS.md`, never in a client's own
file — the repo's `.agents/README.md` maps which tool reads what.
